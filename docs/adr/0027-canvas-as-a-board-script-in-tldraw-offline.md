# Canvas as a board script in tldraw offline, behind CANVAS_BACKEND=desktop

## Context

#14's spike answered its 8 open questions against the running app (tldraw offline 1.20.0, Electron 43, SDK `5.5.0-next` — we build against `^5.4.2`) and recommended "parallel" while two things were unproven: whether a board script's `main.js` can actually reach the MCP server's bridge, and whether a prototype can run sandboxed once served from the MCP server's own HTTP origin. A follow-up comment proved both. #16 asks for the tracer bullet: with `CANVAS_BACKEND=desktop`, `render_graph` draws the frontier graph inside tldraw offline, driven by the same MCP server, bridge and protocol (ADR 0002) — the board script is the bridge client, exactly as the Vite app is today. The ticket's own decision is **replace**: the Vite app stays only until the migration is complete, unlike the spike's "parallel" recommendation for the open-ended state.

## Decision

- **The bridge and protocol do not change.** `CanvasBridge` (`apps/mcp-server/src/bridge.ts`) still owns the WebSocket on `127.0.0.1:4477`; a board script connects to it exactly like the Vite canvas's `BridgeClient` does, over the same envelope schema. `CANVAS_BACKEND=desktop` only changes how the *client* gets onto the canvas — everything server-side of the bridge is unaware which backend it is talking to.

- **`connectBridge` is the one function both backends run.** The Vite app's `useCanvasBridge` hook was a thin React wrapper around one imperative effect (build the `ActivityTracker`, the `BridgeClient` with `createCommandHandlers`, `watchQuestionCards`, `pushActivityWhenQuiet`, start it, resend answered cards on reconnect). That effect is now `apps/canvas/src/bridge/connectBridge.ts`, a plain `(editor, options) => stop` function; `useCanvasBridge` calls it inside `useEffect`, and the board script's `main.js` calls it directly — there is no React tree to hang a hook off outside the editor tldraw offline already mounts. This is the seam that makes "no copied shape or handler logic" true: the board script imports the same `QuestionCardShapeUtil`, `PrototypeShapeUtil`, `hideCollapsedContent`, `createCommandHandlers` and `connectBridge` the Vite app imports, not copies of them.

- **The bundle is esbuild, not Vite.** `apps/canvas/scripts/build-board-script.mjs` bundles two new entry points, `src/board-script/config.entry.ts` and `main.entry.ts`, to `apps/canvas/dist-board-script/{config,main}.js` (`pnpm --filter @tldraw-code/canvas build:board-script`). `tldraw`, `react`, `react/jsx-runtime`, `react-dom` and `react-dom/client` are external — tldraw offline's board scripts resolve these bare specifiers through its own import map to the app's single SDK/React instance (confirmed live: `await import('react/jsx-runtime')` resolves inside a board script, even though it is not one of the bare specifiers `api.imports` documents — only `tldraw`, `react` and `react-dom(/client)` are). `@dagrejs/dagre` and `@tldraw-code/protocol` are not importable there (`Failed to resolve module specifier '@dagrejs/dagre'`, confirmed live), so both are bundled in. The output is **not** `apps/canvas/dist/board-script`: `vite build` empties `dist/` (`emptyOutDir`, the default) on every run and would silently delete a bundle that lived under it, so it gets its own sibling directory instead, `dist-board-script/`, gitignored like `dist/`.
  - `config.js`'s default export (`config.entry.ts`) pushes `QuestionCardShapeUtil`, `PrototypeShapeUtil` and `FrameShapeUtil.configure({ showColors: true })` onto `config.shapeUtils`, sets `config.getShapeVisibility = hideCollapsedContent`, and sets `config.components.TopPanel` to the bridge pill.
  - `main.js`'s default export (`main.entry.ts`) calls `connectBridge(editor, …)` and injects the canvas's own CSS.
  - `config.js` and `main.js` are separate module graphs with no shared module state (tldraw offline's own contract). The bridge pill lives in `config.js`, the live `BridgeClient` in `main.js`; `apps/canvas/src/board-script/bridgeStatusChannel.ts` bridges the two the one way they can share anything for certain — `window` — with a `publishBridgeState`/`subscribeBridgeState` pair (a `CustomEvent`, not a poll) instead of module-scope state, which would silently desync across a `config.js` rebuild.
  - The canvas's `index.css` is baked into `main.js` as a build-time string constant (`__BOARD_CSS__`, esbuild `define`), not a runtime import: esbuild's own CSS handling would emit a separate `.css` asset with nowhere on tldraw offline's page to link it from. `injectBoardStyles` appends it once (guarded by a DOM marker, since a board-script rerun gets a fresh module instance but the same page) and strips the file's `@import url("tldraw/tldraw.css")` — the offline app already loads the SDK's base styles for its own editor.
  - The bridge URL is a second build-time constant, `__BOARD_BRIDGE_URL__` (`CANVAS_BOARD_SCRIPT_BRIDGE_URL` env var at build time), the board-script equivalent of the Vite app's `VITE_CANVAS_BRIDGE_URL`. Neither backend can read the MCP server's own `CANVAS_BRIDGE_PORT` at runtime, since neither is the same process.

- **`CANVAS_BACKEND=desktop` installs the bundle through the Agent API**, in `apps/mcp-server/src/desktop/`:
  - `serverConfig.ts` reads `port` and `token` from tldraw offline's `server.json` (`~/.config/tldraw/server.json`, or `TLDRAW_OFFLINE_SERVER_JSON`) fresh on every call — nothing caches the token across requests.
  - `agentApiClient.ts` is a small HTTP client (`search`, `createDoc`, `exec`, `scriptWorkspace`, `scriptStatus`) that always targets `http://127.0.0.1:<port>` (never `localhost`, so a request cannot leave loopback via DNS) and reads the token through `serverConfig` on every request; its errors quote the server's response, never the request, so the token cannot leak into a log line.
  - `installBoardScript.ts` finds the session document by exact (case-insensitive) name via `api.getDocs({ name })`, or creates it with `docs/create`; opens `script-workspace`; writes `config.js` and `main.js` **to the local filesystem paths the endpoint returns** (`mainJsPath` and its sibling) — the MCP server and tldraw offline run on the same machine, so this is a plain `fs.writeFile`, not another HTTP call; polls `script-status` until `state: "applied"` (or throws on `"error"`/timeout); saves the document.
  - `main.ts` calls this after the bridge starts, behind `if (process.env.CANVAS_BACKEND === 'desktop')`, and never throws past it: same pattern as a bridge port already in use — log to stderr and keep serving MCP.
  - The session document name defaults to `tldraw-code session` (`CANVAS_DESKTOP_DOC_NAME`), directory to tldraw offline's own default (`CANVAS_DESKTOP_DOC_DIR`).

- **Answers to #14's 8 questions**, updated where the tracer bullet found more:
  1. **Custom shapes / consent**: confirmed by this ticket beyond the spike's question card — `QuestionCardShapeUtil`, `PrototypeShapeUtil` and a configured `FrameShapeUtil` all register and render through `config.js` with no consent dialog (agent-written scripts are locally trusted). The prototype *sandbox* question (not just the shape rendering it) is unchanged from the spike: still needs the MCP-server-origin iframe design, out of scope of this ticket.
  2. **Backchannel**: proven in the spike's follow-up (WebSocket 3 ms, fetch 6 ms to a real listener) and now exercised for real by `connectBridge`/`BridgeClient` over the actual bridge, not a stand-in listener.
  3. **Blocking `ask`**: unaffected — `ask.show` is a command like any other; the board script's `QuestionCardShapeUtil` and `watchQuestionCards` are the same code the Vite app runs.
  4. **Screenshot / `read_canvas`**: unaffected by this ticket; `canvas.read` runs through the same `commandHandlers`, still backed by `captureScreenshot`'s browser APIs, which tldraw offline's renderer provides.
  5. **Persistence**: confirmed again end to end — `docs/create` and `helpers.saveDoc()` both worked against a throwaway document created for this ticket's own verification.
  6. **Token**: confirmed and now implemented — read fresh per request from `server.json`, never logged, requests only to `127.0.0.1`.
  7. **Replace or parallel**: the ticket already decided **replace** as the end state; `CANVAS_BACKEND=desktop` is how the two coexist during the migration, not a permanent parallel offering.
  8. **Licence**: unchanged from the spike — the app is only driven through its local Agent API, never embedded or redistributed.

## Considered Options

- **Keep the bridge wiring only in `useCanvasBridge`, and give the board script its own copy**: this is what ADR 0016's "no copied shape or handler logic" acceptance criterion rules out; `connectBridge` is the extraction that avoids it.
- **Share state between `config.js` and `main.js` through an imported module**: tldraw offline documents that the two are separate module graphs and warns against it; `window` (a `CustomEvent`, not a poll) is the one thing both are guaranteed to share.
- **Write the bundle to `apps/canvas/dist/board-script`** (what the ticket's own text suggests): found live, during this ticket's verification, that `vite build`'s `emptyOutDir` deletes it on the next Vite build. `dist-board-script/` avoids the two builds fighting over one directory.
- **`encodeURIComponent` the document id in Agent API URLs**: the id (`tldr:file:<base64url>`) contains `:`; encoding it as `%3A` made the running app answer `404 Document not found`. The app matches the `:id` path segment literally, so the client sends it as is.
- **Have the MCP server build the bundle itself at startup** (import esbuild's JS API into `apps/mcp-server`): adds a heavier runtime dependency and startup latency to every session for a build that only changes when the canvas source changes. A separate `build:board-script` step, read from disk, matches how the Vite build already works.

## Consequences

- Building the board script is a manual (or CI) step, `pnpm --filter @tldraw-code/canvas build:board-script`; `startDesktopBackend` reports a clear, actionable error ("looked in …, run … first") if it was never run, rather than failing obscurely.
- The bundle is built against this repo's `tldraw@^5.4.2` types but runs against whatever SDK tldraw offline actually ships (`5.5.0-next` at spike time) through its import map — a version drift #17/#18 should keep watching; nothing here pins or checks it.
- `@tldraw-code/protocol`'s zod dependency bundles in whole (no tree-shaking across the `tldraw`/`react` external boundary), so `main.js` and `config.js` are ~900 KB each unminified. Acceptable for a tracer bullet; revisit if this backend becomes the default.
- Custom shape props still need real migrations on this backend (spike finding): a schema change with no migration is silently skipped by the config rebuild while an old instance is on the document, even though `script-status` reports `applied`.
- The board script only ever writes in response to a bridge command from the one MCP server session driving it; ADR 0002 already guarantees at most one canvas is active, so no `ctx.app.board.isHost` guard was needed for a session document that becomes shared — a joined participant's own board script would simply fail to reach `127.0.0.1` on *their* machine and stay disconnected, never race the host's writes.
- Verified end to end against the running app in a throwaway document (`/tmp/tldraw-code-e2e-check.tldraw`, outside this repo, deleted from `git status`'s view — nothing about it is committed): installed the bundle, connected, and `render_graph` drew 3 nodes and 2 edges with the right colours and frontier; the bridge pill read "Claude Code connected" while connected and "MCP server not running" once the bridge stopped.
