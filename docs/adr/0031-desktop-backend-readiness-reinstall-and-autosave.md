# Desktop backend: per-command readiness, bundle reinstall, and autosave

## Context

ADR 0030 (#16) got the tracer bullet working: `CANVAS_BACKEND=desktop` installs the canvas as a tldraw offline board script once, at MCP server startup. #17 asks for a session that survives a save, a quit and a reopen: the graph is still there and the next `render_graph` "just works," a rebuilt bundle is picked up without a manual step, a closed app fails fast with a clear message instead of a 10 s timeout, and a document never sits with unsaved changes after a write.

The one-time startup install does not cover any of this on its own. tldraw offline's own contract already does the hard part for reconnecting: the board script travels inside the `.tldraw` file and reruns whenever the document (re)opens, and `BridgeClient` (`apps/canvas/src/bridge/BridgeClient.ts`) already reconnects with backoff on its own. What was missing was something on the MCP server's side that runs *per tool call*, not just at startup: notice a stale bundle, wait out a reconnect after an app restart, fail fast and clearly when tldraw offline is not reachable, and save after a write.

## Decision

- **`DesktopReadiness` (`apps/mcp-server/src/desktop/desktopReadiness.ts`) is the per-call readiness check**, used by a new **`DesktopCanvasBridge`** (`apps/mcp-server/src/desktop/desktopCanvasBridge.ts`) that subclasses `CanvasBridge` and overrides only `request`: `await readiness.ensureReady(() => this.isConnected())`, then the normal `super.request(...)`, then `await readiness.save()` for every command except the two read-only ones (`canvas.read`, `canvas.activity`). `CanvasBridge` and the wire protocol themselves are untouched, exactly as ADR 0030 decided — this is a wrapper the desktop backend opts into, constructed in `main.ts` only when `CANVAS_BACKEND=desktop`.

- **Bundle-staleness detection is a local file comparison, not a version stamp.** `DesktopReadiness` caches the resolved `{docId, workspace}` after the first successful lookup and, on every call, reads the two installed script files straight off local disk (same machine, per ADR 0030) and compares their content byte-for-byte against the freshly built bundle (`readBoardScriptBundle()`, also read fresh every call — a local read is cheap enough not to bother caching). Equal and already connected is the fast path: zero network calls. Different, or nothing readable yet (`ENOENT`), triggers a reinstall (`writeAndApply`, factored out of `installBoardScript.ts` so both the one-time startup install and this per-call check share the same write-wait-save sequence). No digest or explicit version number is embedded in the bundle: the build output is small enough (~900 KB unminified per ADR 0030) that a straight string compare of two files already on disk is simpler than inventing and threading a version identifier through the build, the archive, and a comparison protocol.

- **Reinstalling is what makes a stale bundle "just work" on the next tool call**, live or after an app restart: writing `config.js`/`main.js` again is exactly what reruns the board script (a `config.js` change rebuilds the store and editor; either file changing reruns `main.js`'s effect — ADR 0030, confirmed live during #16), which tears down and recreates the `connectBridge` connection. `ensureReady` waits for that (or an independent restart-caused reconnect) with a plain polling loop against `bridge.isConnected()`, using real timers (`connectTimeoutMs`, default 5 s; `connectPollIntervalMs`, default 100 ms) — deliberately not the same injectable `sleep` used for the apply-wait, so a test cannot accidentally starve Node's timer phase with a synchronous no-op loop.

- **Reachability failures become `CanvasBridgeError(NotConnected)` with an actionable message**, the same error shape and `toolError` formatting every other bridge failure already uses (`server.ts` needed no changes). `findOrCreateDoc`'s two Agent API calls (`getDocs`, `docs/create`) are wrapped once, in `DesktopReadiness`, into one message: *"tldraw offline is not running, or '\<docName\>' is not open in it (\<cause\>). Start tldraw offline and open '\<docName\>', then try again."* Both causes — the app is closed, and the app is open but the session document is not — get the same message rather than two separately diagnosed cases: both are fixed the same way, and both fail within the underlying HTTP call's own timeout (seconds, not the bridge's 10 s command timeout), since nothing here adds an artificial delay before reporting them.

- **Saving after a write is best-effort and silent on failure**, logged to stderr like every other "keep serving" fallback in `main.ts` (a bridge port already in use, a startup install that could not run). A failed autosave does not fail the tool call that already changed the canvas; the next successful write's save catches up. This matches the acceptance criterion's steady state (no unsaved changes after a write) without making an ordinary MCP tool call fail on a transient save hiccup.

- **`main.ts`'s eager startup install now shares the same `DesktopReadiness` and calls `ensureInstalled()`**, the install half of `ensureReady` without the connect-wait, instead of the one-time, unconditional-overwrite `installBoardScript`/`startDesktopBackend` from #16. This means the bundle is checked and, if needed, reinstalled the same way whether that happens at startup or on the first tool call, and the doc/workspace `DesktopCanvasBridge` later reuses is already cached — no redundant Agent API round trip on the first command. `installBoardScript`/`startDesktopBackend` stay exported as a standalone, always-overwrite primitive (their existing tests are unaffected) for a possible future manual "reinstall" entry point, but the live server no longer calls them.

## Considered Options

- **Embed a build version/hash in the bundle and compare that instead of file content**: adds a generator step and a place for the two to drift; a direct content comparison of two ~450 KB files is not slow enough to need a shortcut, and it can never be wrong about what is actually installed.
- **Only check staleness when the bridge is disconnected**: covers a restart, but not the live-dev-loop case the acceptance criteria call out explicitly ("a changed bundle is reinstalled on the next tool call") — rebuilding the canvas while tldraw offline keeps running never disconnects the bridge on its own, so a disconnect-gated check would never notice.
- **Poll `script-status` / re-open `script-workspace` on every call to detect staleness**: works, but costs an Agent API round trip on every single tool call even in the common case where nothing changed; a local file read costs nothing and answers the same question, since the MCP server and tldraw offline already share a filesystem (ADR 0030).
- **Fail the tool call when the post-write save fails**: technically closer to guaranteeing the acceptance criterion on every single call, but turns a save hiccup into a write failure for a canvas change that, in fact, already succeeded — worse for the user than a quiet retry on the next write.
- **Give `CanvasBridge` itself a reconnect-aware `request`**: would blur the "bridge and protocol do not change" line from ADR 0030; a subclass used only by the desktop backend keeps the Vite/WebSocket path exactly as it was.

Verified live against the running app (tldraw offline already open, a throwaway document under `/tmp`, `CANVAS_BRIDGE_PORT`/`CANVAS_BOARD_SCRIPT_BRIDGE_URL` overridden to a port other than the user's own session's 4477): a first command created and opened the session document, installed the board script, waited for it to connect, and saved (`unsavedChanges: false`); editing the built `main.js` on disk and issuing a second command reinstalled it without any manual step, reconnected, and saved again. The app-restart half of #17's first acceptance criterion, and the "app not running" error path, were not exercised live — both require quitting or not having the app running, which risks the user's own session — and are covered by `DesktopReadiness`'s unit tests instead.

## Consequences

- Every command in desktop mode costs at least two local file reads (the built bundle, the installed files) before it reaches the canvas; negligible next to the bridge's own round trip, and zero extra network calls on the fast path.
- `connectTimeoutMs` (default 5 s) is also, in effect, how long a tool call can block *in addition to* the bridge's own request timeout when tldraw offline is slow to reopen a document — acceptable for a local dev tool; **#19 made this the default backend**, so this now applies to every session by default rather than only opt-in ones, still unchanged from its original 5 s.
- The "app not running" and "document not open" cases share one message; a future ticket that wants to tell them apart (e.g. to suggest `docs/create` directly) will need to distinguish them by inspecting the underlying cause, which today's message only quotes, not structures.
